# Очистка каталога и прямой вход в маркет

Выпуск /root/goblin-release-20261109.mtxnup опубликован на cryptogoblin.ru. Маркет работает через PM2 goblin-market из apps/market/.next/standalone/apps/market/server.js, порт 8081. PM2-конфигурация сохранена.

По явному запросу владельца из рабочего каталога полностью удалены 95 шаблонных категорий. На момент очистки товаров, заказов и чатов было 0. Пользователи, балансы, журнал кошелька и настройки не удалялись. Новые категории и подкатегории добавляются через защищённые административные операции. Пользователи по-прежнему могут размещать объявления внутри категорий, созданных администратором.

Автоматическое заполнение createProductionStore отключено: новая или повторно инициализированная база получает пустой каталог. Тестовые категории теперь создаются отдельной fixture, а не фабрикой production.

## Сохранность данных

Применена аддитивная миграция 040_market_catalog_resets.sql. Очистка выполнена CLI reset-market-catalog.js с явным флагом --confirm-clear-existing-categories и постоянным ключом 2026-11-09-owner-catalog-clear. Снимок исходного состояния и популярности хранится в market_catalog_resets. Повтор команды с тем же ключом не удаляет вновь добавленные категории.

Сброс останавливается при наличии объявлений, заказов, чатов, сообщений или проектов, чтобы не разорвать исторические ссылки. Данные проверяются под SQL-блокировкой. Подсчёт посещений теперь проверяет категорию внутри транзакции с общей блокировкой: параллельный запрос не может вернуть счётчик уже удалённой категории после сброса.

Резервная копия до изменения: /root/backups/goblin-20261109.1cv0Yh. База, приложение, PM2, nginx и manifest с SHA-256; права каталога 0700, конфиденциальных файлов 0600. Старый каталог можно восстановить из снимка, но нельзя заменять весь текущий payload или базу устаревшим снимком после новых операций. Восстанавливать следует только согласованные поля каталога после проверки ссылок.

## Вход

Форма /market/login раньше требовала email и отклоняла ник до запроса к backend. Теперь поле принимает логин или email общего аккаунта биржи. Регистр ника не изменяется, email нормализуется отдельно. Неверные учётные данные и временная недоступность разделены в сообщениях. Логин остаётся в форме после неудачной попытки; пароль очищается штатным сбросом формы.

Регистрация сохраняет обязательную проверку email. Требования к новому паролю согласованы с backend: минимум 10 символов, буквы и цифры, максимум 72 байта. Для входа ограничения на длину нового пароля не применяются, чтобы не блокировать существующие аккаунты. Production использует Secure/HttpOnly cookie; локальные HTTP-тесты запускались с отдельной тестовой настройкой COOKIE_SECURE=false.

## Проверки

- 117 backend-проверок прошли локально и на сервере.
- Сборка Next.js на Linux прошла; production npm audit сообщает 0 уязвимостей.
- Изолированная MySQL: все 40 миграций, снимок каталога, конкурентный сброс один раз, отсутствие повторного наполнения, запрет старых посещений, добавление только администратором, сохранение новых категорий при повторной команде, отказ при связанных записях. Реальный bcrypt/JWT-вход по нику и email, отказ неправильного пароля.
- UI на 320/390/768/1440 px с отдельным fixture RPC: пустые аккаунты/услуги, 404 старой категории, неправильный пароль, прямой вход по нику/email, HttpOnly cookie, создание первой категории администратором.
- Production: оба раздела пусты, форма входа принимает текстовый логин, backend read-only smoke проверен. Проверки не вводили реальные пароли клиентов и не создавали тестовых товаров или денежных операций в production.
