# Маркет и гарант в CryptoGoblin

## Что перенесено

Основные сценарии двух исходных проектов работают внутри существующего React/Express приложения, с аккаунтами CryptoGoblin и MySQL. Отдельные Next.js/Fastify/MongoDB процессы не запускаются.

- `/market`: публичный каталог, поиск и объявления; 95 категорий и их разделы из kworkSite.
- `/market/sell`: размещение и приостановка собственных объявлений.
- `/market/orders`: покупки и продажи, защищённая оплата, ручная передача в чате.
- `/market/wallet`: отдельный рублёвый баланс, заявки пополнения/вывода и история.
- `/guarantor`: сделки в USDT, приглашение второй стороны ссылкой, роли покупателя/продавца.
- `/commerce/deals/:id`: условия, резерв, передача, приёмка, возврат, спор, чат и журнал.
- `/manage/commerce`: платежи и сделки для администраторов, разрешение споров.

Админ-раздел использует имеющийся список ADMIN_EMAILS; ссылка находится в основной админке. API находится под `/api/commerce`, существующий nginx уже проксирует этот префикс. `/manage/commerce` выбран специально, чтобы обновление страницы не попадало под API-префикс nginx `/admin`.

## Денежные правила

Рубли не добавляются в криптокошельки. Таблица market_wallets хранит доступный баланс маркета. Покупка резервирует сумму сразу; выплата продавцу выполняется после подтверждения покупателя. Возврат выполняет продавец либо администратор при споре.

Рублёвое пополнение — заявка, а не автоматическое начисление введённой суммы. Администратор подтверждает реальное поступление. Реквизиты выдаёт действующая поддержка. Платёжный провайдер для рублёвых платежей не подключён. Заявка на вывод резервирует рубли; отклонение возвращает их, подтверждение требует фактической выплаты администратором.

USDT резервируются после присоединения контрагента и явного согласия покупателя. Сумма списывается с доступного кошелька и хранится за сделкой до выплаты или возврата. Это отдельный резерв, не wallets.locked_balance: старые P2P и трейдинг используют этот столбец по-разному. Проверяется свободный остаток с учётом существующих блокировок. Повторные финансовые действия не создают повторного списания/выплаты. Все денежные изменения и журнал выполняются одной SQL-транзакцией с блокировками строк.

Открытый спор замораживает средства. Продавец не может подтвердить свою выплату, покупатель не может отменить оплаченный заказ односторонне. Администратор разрешает спор с обязательным объяснением. Комиссия в этой реализации не взимается.

## Что не переносилось в первоначальной версии

Демонстрационные пользователи, объявления и балансы из JSON не импортированы в прод. Не связывались старые аккаунты по совпадению имени. Исходные проекты и Telegram-бот не изменены; его токен и отдельные Telegram/MongoDB сделки не подключались. Каталог пуст до реальных объявлений продавцов. Отдельный модуль рекламных заданий исходного маркета, автоматическая выдача цифровых ключей и фото-вложения Telegram-бота не перенесены; текущая передача и чат текстовые.

## Проверка и выкладка

1. `cd backend && npm test` — проверки переходов, прав и точности сумм.
2. `npm run build` из корня — сборка интерфейса.
3. `cd backend && npm run migrate` — добавочные миграции 012/013, старые миграции не меняются.
4. `COMMERCE_DB_CHECK=1 node scripts/check-commerce.js` — проверка полного денежного цикла на одноразовых QA-аккаунтах, с удалением записей в finally. Не запускается обычным npm test. Требует БД и создаёт только тестовые записи.
5. `COMMERCE_DB_CHECK=1 COMMERCE_HTTP_CHECK=1 node scripts/check-commerce.js` — дополнительно проверяет работающий backend на localhost:3000, запреты чужих сделок и админки.
6. `node scripts/check-commerce-ui.mjs` из корня — локальная браузерная проверка 320–1920 px с явно имитированным API. Требует запущенного Vite на 5178, Chrome и bundled Playwright. Это проверка вёрстки, а не доказательство реальных платежей.

Перед обновлением сохранить build и заменяемые backend-файлы. Перезапускается только goblin-backend. Существующие почта, бот и остальные PM2 процессы не меняются. При откате восстановить старый build и backend-файлы; новые таблицы не удалять, если уже появились реальные сделки или резервы.
